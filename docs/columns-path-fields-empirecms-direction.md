# 栏目路径字段收敛方案（朝帝国 CMS 方向演进）

## 背景

当前 `columns` 表中与栏目 URL / 生成路径相关的字段主要有 3 个：

- `custom_url`
- `route_path`
- `slug`

它们在当前系统中的职责并不清晰：

- `custom_url` 只对链接栏目有明确意义。
- `route_path` 对单页栏目有效，但很多分类栏目此前并没有显式填写，而是由代码规则推导。
- `slug` 在产品分类上承担过一部分 URL 语义，但对单页、新闻栏目、链接栏目并不统一。

这导致当前栏目路径体系更像“代码猜测 + 局部约定”，而不是一个稳定的 CMS 配置模型。

我们的目标不是继续修补这 3 个字段，而是**朝帝国 CMS 的栏目路径模型演进**：

1. 上层栏目路径
2. 本栏目目录
3. 内容页命名规则

也就是让栏目路径生成有明确依据，而不是运行时猜。

---

## 目标

在保留现有系统可迁移性的前提下，逐步演进到下面的模型：

- 栏目路径由栏目配置决定
- 栏目完整路径可稳定推导
- 内容页输出路径可通过规则配置生成
- 旧字段在过渡期承担兼容职责，但不再继续扩展语义

---

## 帝国 CMS 思路如何映射到当前系统

帝国 CMS 的路径体系，本质上是三层：

1. 父级路径基底
2. 当前栏目目录名
3. 当前栏目下内容页命名规则

在当前项目中，建议映射为：

### 1. 父级路径

不建议单独手填一个“上层栏目路径”字段。

原因：

- 手填父路径和手填完整路径容易冲突
- 栏目移动父级后容易产生脏数据
- 这类信息天然适合由树结构递归推导

建议做法：

- 由栏目树关系自动推导父级完整路径
- 不把“父级路径”作为长期人工维护字段

### 2. 本栏目目录

这是未来最核心的新字段，建议新增，例如：

- `dir_name`

含义：

- 只表示当前栏目自己的路径片段
- 不含父路径
- 不含内容页文件名

示例：

- `products`
- `steam-traps`
- `about-us`
- `industries`

### 3. 内容页命名规则

这是未来第二个关键字段，建议新增，例如：

- `detail_rule`

示例值：

- `{id}.html`
- `{slug}.html`
- `{slug}/index.html`
- `{yyyy}/{mm}/{id}.html`

该字段只对“带内容项的栏目”生效，例如产品栏目、新闻栏目等。

---

## 对现有 3 个字段的处理原则

这部分是本方案的重点。

### `custom_url`

未来定位：

- **只保留给链接栏目**

适用场景：

- `custom_link`

说明：

- 这里的“链接栏目”不等于“外链栏目”
- 它既可以指向站外完整 URL
- 也可以指向站内路径，例如 `/about-us/`
- 甚至可以指向锚点或特定资源地址

不再承担：

- 普通栏目公开路径
- 分类栏目路径
- 单页栏目路径

结论：

- 保留字段
- 明确语义收窄为“链接栏目目标地址”
- 后续校验上约束为“仅 `custom_link` 允许填写”

### `route_path`

未来定位：

- **过渡期的栏目完整公开路径缓存字段**

它的职责应当变成：

- 保存系统根据栏目树和 `dir_name` 计算出的完整栏目路径
- 在迁移阶段作为运行时读取的主要路径字段

示例：

- `/about-us/`
- `/products/steam-traps/`
- `/news/`
- `/service/`

注意：

- 长期看，`route_path` 不应该再让用户直接自由输入任意内容
- 它更适合作为系统计算结果
- 过渡期可以保留编辑能力，用于兼容历史数据

结论：

- 保留字段
- 从“混合用途字段”收敛为“完整栏目路径”
- 在未来新模型中逐步转为系统生成值

### `slug`

未来定位：

- **从栏目表中直接移除**

原因：

- 它与未来 `dir_name` 高度重叠
- 它不能清晰表达“完整栏目路径”
- 它只适合表达“单个路径片段”
- 目前在栏目表中只对部分产品分类有效，跨栏目类型不统一
- 继续保留只会让栏目路径体系长期处于双轨状态

处理原则：

- 不做长期兼容
- 不再让 `columns.slug` 继续参与栏目公开路径逻辑
- 需要迁移的数据一次性迁到新字段

推荐方式：

- 新增 `dir_name`
- 将 `columns.slug` 中仍有价值的数据迁移到 `dir_name`
- 完成运行时代码切换后，直接删除 `columns.slug`

说明：

- 内容项表中的 `slug` 不在本次范围内
- 产品详情、新闻详情等内容项仍然可以继续保留自己的 `slug`

---

## 推荐的未来字段模型

建议栏目路径体系最终收敛为：

- `custom_url`
  - 链接栏目目标地址
- `dir_name`
  - 当前栏目目录名
- `route_path`
  - 系统计算出的完整栏目路径
- `detail_rule`
  - 内容页命名规则

可选补充字段：

- `route_mode`
  - 用于区分“栏目页路径模式”是否目录化

但第一阶段不建议上太多字段，避免一次性设计过重。

---

## 字段职责对照表

### 当前阶段

| 字段 | 当前问题 | 未来处理 |
| --- | --- | --- |
| `custom_url` | 只对链接栏目有意义，但语义未被严格限制 | 收窄为链接栏目目标地址 |
| `route_path` | 有时是手填，有时是代码推导，有时为空 | 收敛为栏目完整公开路径 |
| `slug` | 只在部分产品分类有效，语义不统一 | 迁移到 `dir_name` 后直接移除 |

### 目标阶段

| 字段 | 职责 |
| --- | --- |
| `custom_url` | 链接栏目目标地址 |
| `dir_name` | 当前栏目目录名 |
| `route_path` | 完整栏目路径（系统生成/缓存） |
| `detail_rule` | 内容页命名规则 |

---

## 推荐演进顺序

### 第一阶段：先收敛旧字段语义

目标：

- `custom_url` 仅链接栏目可用
- `route_path` 成为栏目公开路径主字段
- `slug` 退出栏目 URL 主链路

这一阶段不要求立刻引入帝国 CMS 全套模型，但要先停止旧字段继续发散。

### 第二阶段：引入 `dir_name`

目标：

- 栏目改由 `dir_name` 表达目录片段
- 目录层级由父子栏目关系 + `dir_name` 生成
- `route_path` 开始由系统推导

### 第三阶段：引入 `detail_rule`

目标：

- 内容页输出路径不再写死在生成器里
- 产品、新闻等内容项路径规则进入配置层

### 第四阶段：删除 `columns.slug`

前提：

- 所有栏目类型都已改用 `dir_name`
- 运行时和静态生成不再依赖栏目 `slug`
- `slug` 数据已完成迁移

---

## 为什么不建议现在直接删除这 3 个字段中的某一个

因为当前系统还处在过渡态：

- `custom_url` 对链接栏目仍有真实价值
- `route_path` 是未来最适合承接“完整栏目路径”的字段
- `slug` 虽然应被删除，但删除前仍需要一次明确迁移

如果现在直接删字段，风险是：

- 静态生成逻辑回归
- 旧模板/旧链接断裂
- 数据迁移难以分阶段验证

所以更稳妥的策略是：

- **先收敛语义**
- **再引入新字段**
- **完成数据迁移**
- **直接删除 `columns.slug`**

---

## 本文档的结论

朝帝国 CMS 方向演进时，这 3 个现有字段建议这样处理：

- `custom_url`：保留，只给链接栏目使用
- `route_path`：保留，作为过渡期和未来阶段的栏目完整路径字段
- `slug`：迁移到 `dir_name` 后直接删除，不保留长期兼容

也就是说：

- 不是“这 3 个字段继续凑合用”
- 也不是“现在立刻删掉其中某个”
- 而是把它们纳入一条清晰的演进路径

最终模型应该是：

- 链接栏目用 `custom_url`
- 栏目目录片段用 `dir_name`
- 栏目完整路径用 `route_path`
- 内容页文件规则用 `detail_rule`

这才是真正朝帝国 CMS 的方向走，而不是继续在旧字段上堆临时逻辑。
