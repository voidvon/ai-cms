# 全站统一搜索方案

评估日期：2026-06-20

## 1. 结论

本项目全站搜索的最优方案，不是继续使用前端 `Pagefind`，也不是分别去查产品表、新闻表，而是：

- 以“内容模型 + 栏目”作为统一抽象
- 在后端提供统一搜索接口 `/api/search`
- 在数据库中建立“搜索文档层”
- 使用 SQLite `FTS5` 作为全文索引
- 通过“应用层增量同步 + 全量重建命令”维护索引

这套方案最符合当前项目的约束：

- 现有技术栈是 `Node.js + Fastify + SQLite`
- 项目目标是帝国 CMS 式“栏目 + 模型 + 模板 + 静态发布”
- 搜索对象不止一个物理表，而是多个内容模型、多个翻译表、多个栏目层级

简化后的结论可以概括为一句话：

**业务数据继续保存在原业务表中，搜索只查询专用的搜索文档与全文索引。**

## 2. 为什么不直接搜索原表

如果继续沿用“每次搜索时，分别去产品表、新闻表、翻译表、栏目表现场拼接”的做法，会出现以下问题：

- 查询逻辑分散，产品和新闻各做一套
- 多语言字段需要动态回退，SQL 和服务层都容易变复杂
- 搜索结果难以统一排序
- 标题、编号、摘要、正文的权重不好控制
- 后续新增案例、下载、招聘等内容模型时，还要继续加分支

这类实现更像“定制网站代码”，不是“可持续扩展的 CMS 搜索层”。

从帝国 CMS 式心智模型看，正确的方向应该是：

- 前台搜索的是“内容”
- 内容来自不同模型
- 模型背后可以有不同存储表
- 但搜索层不应该暴露这些底层差异

也就是说，搜索系统应该面向“统一内容文档”，而不是面向“若干张原始业务表”。

## 3. 推荐架构

推荐拆成两层：

1. `search_documents`
2. `search_documents_fts`

其中：

- `search_documents` 是普通表，保存搜索结果所需的结构化文档
- `search_documents_fts` 是 `FTS5` 虚拟表，保存全文索引

这两层的职责不同。

### 3.1 search_documents

这张表不是业务主表，也不是后台编辑表，而是“搜索投影表”。

它保存的是搜索真正需要的数据，而不是把产品、新闻所有字段完整复制一份。建议字段如下：

- `id`
- `model_code`
- `entry_id`
- `language_code`
- `column_id`
- `category_id`
- `title`
- `summary`
- `body_text`
- `code`
- `category_name`
- `url`
- `cover_image`
- `is_visible`
- `publish_status`
- `published_at`
- `updated_at`

字段说明：

- `model_code`：区分 `product`、`news`，未来也可扩展为 `case`、`download`
- `entry_id`：对应原业务记录 ID
- `language_code`：按语言建立独立搜索文档，避免查询时才临时做语言回退
- `body_text`：正文去 HTML 后的纯文本
- `url`：最终前台访问地址，避免搜索命中后再临时拼链接

这张表的核心意义是：

- 对不同模型做统一封装
- 对多表数据做预先展开
- 给接口层返回统一结果结构

### 3.2 search_documents_fts

这张表使用 SQLite `FTS5`，只承担全文搜索职责。

建议索引字段：

- `title`
- `summary`
- `body_text`
- `code`
- `category_name`

常见做法是：

- `search_documents` 保存结构化结果数据
- `search_documents_fts` 保存可全文检索字段
- 搜索时先查 `FTS5`，再关联 `search_documents`

这样做比“所有内容直接在原表 `LIKE` 搜索”更标准，也更容易做相关性排序。

## 4. 为什么这种冗余是合理的

搜索系统中的冗余通常是有意设计，不是坏味道。

原因很简单：

- 业务存储追求规范化和真实数据维护
- 搜索存储追求检索速度、排序能力和统一查询模型

因此，搜索层复制的不是“完整业务数据”，而是“搜索投影”。

应当避免的做法是：

- 复制所有原始字段
- 把索引表当主表来改
- 让后台编辑依赖索引表

应当坚持的原则是：

- 原业务表才是真实数据源
- 搜索表可以重建
- 索引损坏时可以全量回刷

所以，这种冗余是受控冗余，不是失控冗余。

## 5. 同步机制

索引层不会天然自动同步，必须由系统显式维护。

本项目最推荐的同步方案是：

- 应用层增量同步
- 全量重建命令兜底

不建议优先采用纯数据库触发器方案，因为本项目搜索文档往往来自多张表拼装：

- 主内容表
- 多语言表
- 栏目表
- 分类表
- URL 规则

把这些复杂逻辑全部塞进 SQLite trigger，可维护性会很差。

### 5.1 增量同步触发时机

以下操作都应触发重建对应搜索文档：

- 新增内容
- 修改内容
- 删除内容
- 发布状态变化
- 显示状态变化
- 标题、摘要、正文、产品编号变化
- 内容所属栏目变化
- 栏目路径变化
- 详情 URL 规则变化
- 多语言翻译内容变化

这里要注意一点：

搜索结果里不仅有“搜什么”，还有“点到哪里去”。  
因此只要会影响最终 URL 或展示标题的变化，也应同步更新搜索文档。

### 5.2 全量重建

系统还应提供一个独立命令，例如：

`npm --prefix system/server run search:rebuild`

它的职责是：

- 清空现有搜索文档和全文索引
- 重新扫描所有可搜索模型
- 重新生成所有语言版本的搜索文档
- 重建全文索引

这个命令是必要的，因为它可以用于：

- 首次上线索引
- 修复历史脏数据
- 模板或 URL 规则大改后的回刷
- 搜索相关 bug 修复后的重建

## 6. 搜索文档的生成原则

搜索文档不应按“物理表”生成，而应按“逻辑内容模型”生成。

当前项目建议至少纳入：

- `product`
- `news`

未来可以自然扩展：

- `case`
- `download`
- `job`
- 其他绑定到内容模型的栏目

每条业务内容在进入搜索层前，都先被映射成统一文档：

- 它属于哪个模型
- 它属于哪个栏目
- 它在哪个语言版本下可见
- 它的标题、摘要、正文纯文本是什么
- 它最终跳转地址是什么

这样搜索服务就不再关心底层到底来自哪张物理表。

这更符合“栏目是核心组织单元、内容模型驱动内容类型”的项目方向。

## 7. 接口设计建议

建议提供统一接口：

`GET /api/search`

建议参数：

- `q`：搜索关键词
- `lang`：语言代码
- `models`：可选，限定模型，如 `product,news`
- `page`：页码
- `pageSize`：每页条数

建议返回结构：

```json
{
  "items": [
    {
      "modelCode": "product",
      "entryId": 123,
      "languageCode": "zh-CN",
      "title": "Steam Trap",
      "summary": "Product summary",
      "url": "/products/steam-trap/",
      "coverImage": "/upload/xxx.jpg",
      "categoryName": "Products"
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 10,
    "total": 58
  }
}
```

这样前端的全局搜索组件只需要调用一个统一接口，不需要知道产品、新闻分别怎么搜索。

## 8. 排序与权重建议

统一搜索的关键不只是“能搜到”，还包括“搜到后排得像样”。

建议权重策略如下：

- 产品编号精确匹配：最高
- 标题匹配：高
- 摘要匹配：中
- 分类名称匹配：中
- 正文匹配：低

对新闻类内容，可以再加一层轻量时间因子：

- 同等匹配分数下，较新的新闻优先

但不要让“发布时间”压过“文本相关性”，否则会把明显不相关的新内容排到前面。

## 9. 多语言策略

本项目不建议在搜索时才做复杂的多语言动态拼接。

更好的方式是：

- 按语言生成独立搜索文档
- 搜索时优先查当前语言
- 没有命中时再决定是否提供默认语言结果

这样做的优点：

- 搜索逻辑更简单
- 排序更稳定
- 结果更可预期
- 不需要在查询阶段做大量语言回退判断

## 10. 与当前实现的关系

当前现状大致如下：

- 前端全局搜索组件仍依赖 `Pagefind`
- 后端只有产品搜索接口
- 新闻还没有统一接入搜索 API

因此后续改造建议分两步：

### 阶段一：后端统一搜索能力落地

- 增加 `search_documents`
- 增加 `search_documents_fts`
- 新增统一搜索服务
- 新增 `/api/search`
- 增加全量重建命令

### 阶段二：前端搜索组件切换

- 保留现有全局搜索 UI 组件
- 将搜索请求从 `Pagefind` 切换到 `/api/search`
- 前端不再直接依赖静态索引文件

这样可以保持当前组件结构基本不变，只替换搜索数据来源。

## 11. 不推荐的方案

以下方案不建议作为正式架构：

### 11.1 直接分别搜索产品表、新闻表

问题：

- 服务层分支越来越多
- 结果难统一
- 后续新增内容模型成本高

### 11.2 一张普通大杂烩表再配 `LIKE`

问题：

- 只是把复杂度搬到另一张表
- 全文能力弱
- 排序和性能都不理想

### 11.3 直接上 Elasticsearch / OpenSearch

问题：

- 架构成本偏高
- 运维复杂度显著增加
- 对当前 SQLite 单体项目来说过重

对于本项目当前阶段，这不是性价比最高的方案。

## 12. 最终建议

本项目全站搜索的推荐正式方案是：

- 使用统一搜索文档层，而不是按原表分别查询
- 使用 `SQLite FTS5`，而不是停留在 `LIKE` 搜索
- 使用应用层同步 + 全量重建，而不是依赖复杂 trigger
- 使用统一 `/api/search`，而不是多个模型各自暴露搜索接口

这套方案的优点是：

- 更符合帝国 CMS 式“栏目 + 模型驱动”架构
- 能兼容产品、新闻以及后续新增模型
- 查询能力和排序能力明显优于现状
- 不需要引入额外搜索服务，复杂度可控

如果后续数据规模和搜索复杂度继续提升，再评估是否迁移到专用搜索引擎；但在当前阶段，`统一搜索文档层 + SQLite FTS5` 是最均衡、最标准、也最适合本项目的一条路线。
