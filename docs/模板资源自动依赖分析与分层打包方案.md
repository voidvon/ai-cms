# 模板资源自动依赖分析与分层打包方案

## 状态

本文档描述的是当前已落地实现，不是讨论稿。

当前系统已经完成以下收敛：

- 模板源码真源为 `tsx_source + css_source`
- `global_css_source / published_global_css_source` 已完成数据迁移并从正式表结构中删除
- 静态构建不再依赖人工标记“全局样式/局部样式”
- 资源归属由静态构建器基于模板依赖分析自动决定

当前前台静态资源输出目录仍为：

- `html/assets/cms-templates/`

## 目标

当前方案的目标是：

- 不按产品、新闻、服务等业务名硬编码 bundle 规则
- 不再让数据库字段表达资源发布作用域
- 以模板依赖图作为资源归并真源
- 以静态生成目标为单位做稳定、可解释的资源分层

## 当前数据模型

当前模板数据模型已经收敛为：

- `tsx_source`
- `css_source`
- `published_tsx_source`
- `published_css_source`

其中：

- `tsx_source` 表示模板结构与渲染逻辑
- `css_source` 表示模板样式源码
- 模板是最小资源单元
- 样式是否进入站点共享、模板共享、家族共享或组内独占，不由数据库字段决定

历史双槽位样式迁移说明：

- 旧库中的 `global_css_source / published_global_css_source` 会先合并到主样式字段
- 合并完成后再重建表结构删除旧列
- 当前正式表结构中已不存在这些旧字段

## 当前分析单位

资源分析单位不是单个页面 URL，而是 `render_group`。

当前 `render_group` 由静态生成目标显式传入运行时，典型包括：

- `site-home`
- `single-page-column-<id>`
- `column-<id>-list`
- `column-<id>-detail`

也就是说，分析单位是：

- 首页
- 某单页栏目
- 某根栏目下的列表页族
- 某根栏目下的详情页族

而不是逐个详情页 URL 单独建组。

这样做的原因是：

- 同一静态生成目标通常复用同一入口模板和组件树
- 逐页分析性能成本更高，且收益有限
- 按组分析更符合栏目驱动的 CMS 架构

## 当前依赖采集逻辑

当前依赖采集发生在模板运行时准备阶段，但分析本身不是逐页渲染采样，而是模板级递归分析。

主流程如下：

1. 静态生成器为当前目标构造 `render_group`
2. 运行时解析该组对应的入口模板
3. 从入口模板的 `tsx_source` 中提取组件引用
4. 递归遍历组件引用关系
5. 把入口模板和其依赖组件都视作模板节点
6. 为每个模板节点收集自己的 `css_source`
7. 得到 `render_group -> styleCodes` 关系

当前组件引用提取只处理可静态识别的字面量引用，例如：

- `#component("xxx")#`
- `component("xxx")`

因此当前方案默认要求：

- 组件树基本稳定
- 不鼓励大量运行时动态组件名拼接

## 当前 bundle 分层

当前已实现四层逻辑：

### 1. `site-shared`

适用于被全部 `render_group` 使用的资源。

当前产物命名：

- `site-shared.css`

### 2. `template-shared`

适用于只被同一入口模板族复用、且覆盖多个 `render_group` 的资源。

当前产物命名：

- `template-<template-code>.css`

### 3. `family-shared`

适用于只在同一页面家族内复用、且覆盖多个 `render_group` 的资源。

当前产物命名：

- `family-<family-key>.css`

### 4. `group-only`

适用于只在单个 `render_group` 内使用的资源。

当前产物命名：

- `group-<render-group-key>.css`

## 当前归并规则

当前实现采用可解释的阈值规则，不做复杂聚类。

判定顺序如下：

1. 如果某资源被全部 `render_group` 使用，进入 `site-shared`
2. 如果某资源只被同一入口模板族使用，且覆盖多个组，进入 `template-shared`
3. 如果某资源只被同一 `familyKey` 使用，且覆盖多个组，进入 `family-shared`
4. 其余资源进入 `group-only`

这里的 `familyKey` 由静态生成器传入，当前主要由：

- `pageKind`
- `columnKind`
- 栏目上下文

组合推导。

## 当前 HTML 注入方式

当前 HTML 中不会直接写死某个页面 CSS 文件名。

运行时会先写入占位符，再在静态资源输出阶段替换为实际 bundle：

- `<!--cms-tsx-styles:...-->`

替换时依据的是当前页面所属的 `render_group`，而不是页面 URL。

这意味着：

- 同一入口模板的不同页面可以共享同一个模板包
- 不同栏目家族可以命中不同的共享层
- 首页、列表、详情、单页可以落到不同组合

## JS 处理

当前模板输出中的可执行内联脚本也已经统一处理为：

- 抽离到独立 JS 文件
- 使用 `esbuild` 压缩
- HTML 中替换为外链 `<script src="...">`

保留内联的例外是：

- `application/ld+json`

这是有意保留的，不属于普通交互脚本。

## 当前数据库迁移策略

当前样式迁移分两步：

### 1. 数据迁移

若旧表仍存在双槽位字段：

- 把 `css_source + global_css_source` 合并回 `css_source`
- 把 `published_css_source + published_global_css_source` 合并回 `published_css_source`
- 把 `template_versions.css_source + template_versions.global_css_source` 合并回 `template_versions.css_source`

### 2. 结构迁移

完成数据迁移后：

- 重建 `templates`
- 重建 `template_versions`
- 删除旧样式列

迁移逻辑要求可重复执行，不允许因旧列已删除而再次报错。

## 当前限制

当前方案已可用，但仍有明确边界：

### 1. 依赖提取基于静态字面量引用

如果模板大量使用动态组件名，当前分析准确率会下降。

### 2. family 层仍是轻量规则

当前 `family-shared` 已实现，但仍是基于稳定键的简单归并，不是复杂统计聚类。

### 3. 迁移兼容代码仍保留在服务层

当前仓库仍保留少量旧字段探测和迁移代码，用于兼容历史数据库。
这部分不是运行时主链路依赖，但仍属于迁移辅助代码。

## 禁止事项

后续开发中禁止重新引入以下做法：

- 恢复 `global_css_source`
- 恢复“模板样式 / 全局样式”双编辑入口
- 在 bundler 中写死 `product/news/service` 规则
- 回到逐页面 URL 采样式依赖的主流程
- 在数据库字段中直接表达“进 shared.css / 进 page.css”

## 结论

当前模板资源系统已经从“字段预先指定发布作用域”切换为“模板依赖驱动的自动归并”。

可以把当前正式规则概括为：

- 模板真源是 `TSX + CSS`
- 模板节点是最小资源单元
- `render_group` 是分析单位
- 组件依赖图是归并依据
- bundle 分层由构建器自动决定

这是当前项目在模板资源层面对“数据库模板真源 + 栏目驱动 + 静态发布”方向的正式实现。
