# 栏目 + 内容模型架构分析

## 1. 背景

这份文档用于回答两个问题：

1. 当前项目现在到底是不是“栏目统一表 + 内容模型独立表”的结构。
2. 如果要恢复成更接近帝国 CMS 的“栏目 + 内容模型”模式，应该恢复成什么样，哪里要改，风险在哪里。

本文分为两类结论：

- `已确认事实`：直接根据当前仓库代码与当前数据库结构确认。
- `参考性结论`：根据帝国 CMS 常见实现方式、社区普遍认知和本项目需求抽象出的设计逻辑，用于方案参考，不等同于逐字复刻帝国 CMS 源码。

## 2. 当前项目已确认事实

### 2.1 当前不是“栏目表 + 独立内容表”结构

当前运行结构已经演变成“统一 `columns` 表同时存栏目和内容”。

依据：

- `system/server/src/services/columns.mjs`
  - `ensureColumnsSchema()` 创建了 `columns` 和 `column_translations`。
  - `columns` 表中同时存在：
    - 栏目字段：`parent_id`、`route_path`、`show_in_nav`
    - 内容字段：`content_html`、`summary`、`images`、`primary_image`
    - 类型字段：`source_type`、`node_type`、`column_kind`
- `system/server/src/services/columns.mjs`
  - `CONTENT_SOURCE_TYPE_BY_MODEL` 中定义：
    - `product -> product_item`
    - `news -> news_item`
  - `CATEGORY_SOURCE_TYPE_BY_MODEL` 中定义：
    - `product -> product_column`
    - `news -> news_column`
    - `corporation -> corporation_column`
- `createContentColumn()` 直接向 `columns` 插入内容记录，且写入：
  - `node_type = 'content'`
  - `column_kind = 'content'`
- `listContentColumnsPaged()` / `getContentColumnById()` 查询内容时，也是从 `columns` 里按 `node_type = 'content'` 过滤。

结论：

- 当前“栏目”和“内容详情”不是两张业务表。
- 它们只是 `columns` 表里的两类记录。

### 2.2 当前还保留了“内容模型”页面，但它并不是真正的模型驱动架构

当前 `/admin/content-models` 页面存在，但本质上只是“字段展示和字段配置页”，不是“完整内容模型管理器”。

依据：

- `system/server/src/services/content-models.mjs`
  - 内置了两个模型：
    - `product`
    - `news`
  - 并写死了：
    - `product -> source_table: products`
    - `news -> source_table: news`
- `readModelFields()` 通过 `PRAGMA table_info(source_table)` 读取字段。
  - 也就是说，页面字段来源依赖某张真实表的表结构。
- `system/server/src/routes/api/content-models.mjs`
  - 目前只有：
    - 列表
    - 详情
  - 没有：
    - 创建模型
    - 删除模型
    - 建表
    - 栏目绑定模型
- `system/admin/src/pages/ContentModelsPage.tsx`
  - 页面上只支持查看模型和调整字段配置。
  - 没有“新增模型”“新增字段”“生成数据表”“栏目绑定”的完整操作。

结论：

- 当前的“内容模型”更像一个“字段配置中心”。
- 它还不是“用户可自定义创建内容模型，并让栏目绑定某个模型表”的架构。

### 2.3 当前栏目页仍然是固定模型分支，不是通用模型绑定

当前栏目页仍按固定类型工作，而不是按用户定义模型动态工作。

依据：

- `system/admin/src/pages/ColumnsPage.tsx`
  - 新增一级栏目时，模型下拉只有：
    - `product`
    - `news`
    - `corporation`
- 产品和新闻有独立表单组件：
  - `ProductFormDialog`
  - `NewsFormDialog`
- 分类编辑也仍按固定类型拆开：
  - `ProductCategoryFormDialog`
  - `NewsCategoryFormDialog`
  - `CorporationCategoryFormDialog`

结论：

- 当前后台不是“模型驱动的通用栏目/内容系统”。
- 当前后台仍然是“产品/新闻/公司栏目”三套固定业务类型。

### 2.4 当前数据库实际结构也支持上面的判断

当前 `data/site.sqlite` 中实际存在：

- `columns`
- `column_translations`
- `content_models`
- `content_model_fields`

但当前业务主流程已经不再把 `products` / `news` 当作主存储结构使用，而是迁移进了 `columns`。

`system/server/src/services/columns.mjs` 中存在以下迁移逻辑：

- `migrateLegacyContentIntoColumns()`
- `migrateLegacyProductContent()`
- `migrateLegacyNewsContent()`

这说明这次改动不是“顺手兼容”，而是明确把旧内容表迁进了统一 `columns`。

## 3. 帝国 CMS 的参考性逻辑

以下不是对帝国 CMS 源码逐行复述，而是对其典型信息架构的抽象总结。

### 3.1 栏目和内容模型是两个层次

帝国 CMS 的核心思想通常可以理解为：

- 栏目统一管理站点树形结构。
- 内容模型定义“这一类内容长什么样”。
- 栏目绑定某个内容模型。
- 某栏目下发内容时，内容写入该模型对应的数据表。

也就是说：

- 栏目解决的是“放在哪、怎么组织、访问路径是什么、模板怎么套”。
- 模型解决的是“字段有哪些、数据存哪里、录入表单长什么样”。

### 3.2 栏目通常统一存一张表

参考帝国 CMS 的常见做法，栏目一般统一保存在一张栏目表中，负责：

- 树形父子关系
- 栏目名称
- 栏目路径
- 栏目类型
- 栏目模板
- 是否终极栏目
- 是否外部链接
- 所属模型

这类栏目表本身不应该承担“内容正文、摘要、图片列表”等详情字段。

栏目表的本质职责是：

- 站点结构
- 导航结构
- 路由结构
- 模板绑定入口

### 3.3 内容模型通常对应独立数据表

帝国 CMS 的典型思路是：

- 一个内容模型对应一套字段定义
- 一个内容模型对应一张或一组数据表

例如：

- 新闻模型 -> 新闻表
- 产品模型 -> 产品表
- 招聘模型 -> 招聘表
- 下载模型 -> 下载表

这样做的好处是：

- 每种内容的字段可以不同
- 后台表单可以按模型动态生成
- 列表页和详情页可以按模型渲染
- 业务不会被强行塞进一个“万能内容表”

### 3.4 栏目绑定模型，而不是内容绑定栏目类型代码

帝国式设计里更关键的一点是：

- 栏目应该绑定某个模型
- 内容记录只需要知道自己所属栏目

从业务视角看，流程通常是：

1. 先创建内容模型。
2. 给模型定义字段。
3. 给栏目指定模型。
4. 在栏目下发布内容。

这样系统可以自然支持：

- 新增“案例模型”
- 新增“资料下载模型”
- 新增“招聘模型”
- 新增“FAQ 模型”

而不用改死在 `product/news/corporation` 这几个枚举里。

### 3.5 单页、外链、封面栏目通常是栏目类型，而不是内容模型

帝国 CMS 风格里，一般会把下面几种东西看作“栏目类型”，而不是“内容模型”：

- 外部链接栏目
- 单页栏目
- 封面栏目
- 纯列表栏目

因为它们不是“可反复新增很多内容记录的数据模型”，而是栏目自身的展示方式。

这点对本项目也很重要：

- `single_page`
- `custom_link`
- `contact_page`

更适合作为栏目类型存在，不适合作为内容模型表。

## 4. 当前项目和帝国式逻辑的主要差异

### 4.1 当前项目把“栏目”和“内容”揉进了一张表

这会带来几个后果：

- 栏目表结构越来越重
- 栏目记录和内容记录混在一起，语义模糊
- 查询时处处要分 `node_type`
- 多模型扩展时，会不断往 `columns` 上继续堆字段

这和“栏目统一表 + 模型独立表”的思路是相反的。

### 4.2 当前 `content_models` 不是驱动核心业务的中心对象

现在的 `content_models`：

- 不能创建完整模型
- 不能自动建表
- 不能让栏目自由绑定
- 不能驱动通用内容录入页

所以它当前只是“辅助元数据”，不是系统核心。

### 4.3 当前后台是固定业务页，不是动态模型后台

现在后台的内容录入依赖：

- 产品表单
- 新闻表单
- 公司栏目表单

这意味着如果你新增“案例模型”，就必须继续写：

- `CaseFormDialog`
- `cases.mjs`
- `case-categories.mjs`
- 列表页
- API

这和你想要的“用户自己创建模型，再绑定到栏目”目标不一致。

## 5. 适合本项目的目标架构

如果要恢复成你说的“像帝国 CMS 那样”的模式，我建议目标不是简单回退到旧代码，而是恢复成下面这套更稳的结构。

### 5.1 栏目仍然统一一张表

保留统一栏目表是对的。

建议 `columns` 只承担：

- 栏目树结构
- 栏目名称与多语言名称
- 栏目路径
- 导航属性
- 栏目类型
- 模板绑定
- 绑定的内容模型 ID

建议保留的栏目类型：

- `list`
- `cover`
- `single`
- `link`
- `form`

或者继续沿用当前项目表达，但不要再把内容详情塞进栏目表。

### 5.2 内容模型应成为一级核心对象

建议 `content_models` 升级为真正的模型定义表，至少包含：

- `id`
- `code`
- `name`
- `description`
- `table_name`
- `status`
- `is_system`
- `supports_column`
- `supports_list`
- `supports_detail`
- `created_at`
- `updated_at`

其中：

- 系统模型可以有：产品、新闻
- 用户模型可以新增：案例、招聘、资料下载、FAQ 等

### 5.3 字段配置表继续保留，但要从“展示字段”升级成“建模字段”

当前 `content_model_fields` 可以保留，但职责要升级。

建议它不仅描述 UI 配置，还要描述真实字段定义，例如：

- `field_name`
- `field_label`
- `field_type`
- `db_type`
- `is_required`
- `is_translatable`
- `is_listed`
- `is_editable`
- `default_value`
- `settings_json`

这样它才能真正用于：

- 创建数据表
- 生成录入表单
- 生成列表列配置
- 生成详情上下文

### 5.4 内容数据应存入模型对应的数据表

建议每个内容模型对应自己的实际内容表。

例如：

- `content_product`
- `content_news`
- `content_case`
- `content_job`

每张表至少包含通用结构字段：

- `id`
- `column_id`
- `title` 或 `name`
- `slug`
- `sort_order`
- `is_visible`
- `published_at`
- `created_at`
- `updated_at`

模型自己的个性字段按模型定义补充。

### 5.5 多语言建议采用“主表 + 翻译表”

考虑到当前项目已经是多语言站点，建议继续沿用“主表 + translations 表”的模式。

例如：

- `content_product`
- `content_product_translations`

翻译表可存：

- `content_id`
- `language_id`
- `title`
- `summary`
- `content_html`
- SEO 字段
- 其他允许翻译的模型字段

这样会比把所有语言字段直接打平到主表更稳。

### 5.6 栏目绑定模型的方式

这里有两个可选方案。

方案 A：直接在 `columns` 表上加 `content_model_id`

优点：

- 简单
- 查询方便

缺点：

- 一个栏目只能绑定一个模型

方案 B：增加 `column_model_bindings`

优点：

- 扩展性更强

缺点：

- 当前项目大概率用不上多绑定，复杂度偏高

对当前项目，我更建议：

- 先用方案 A
- 即在 `columns` 上增加 `content_model_id`

原因是这和帝国式“一个栏目归属一个模型”的主逻辑更一致，也最容易落地。

## 6. 后台应该怎么表现

### 6.1 `/admin/content-models` 应该升级成真正的数据模型中心

建议这个页面最终支持：

- 新增模型
- 编辑模型基本信息
- 新增字段
- 调整字段顺序
- 配置字段类型
- 配置是否参与翻译
- 生成或更新模型数据表
- 查看已绑定的栏目

这时 `/admin/content-models` 就不再只是“看字段”，而是“定义系统内容形态”的入口。

### 6.2 栏目页应该从“固定模型”改成“绑定模型”

当前栏目新增页里模型选项是固定写死的：

- 产品
- 新闻
- 公司

目标应改成：

- 栏目类型
- 绑定内容模型
- 模板绑定

其中：

- 如果栏目类型是 `single/link`，则不需要内容模型
- 如果栏目类型是 `list/cover`，则必须绑定内容模型

### 6.3 内容列表和内容编辑页要变成模型驱动

当前是固定组件：

- 产品列表/表单
- 新闻列表/表单

目标应改成：

- 按栏目读取其 `content_model_id`
- 根据模型字段定义动态渲染：
  - 列表表头
  - 搜索项
  - 编辑表单
  - 翻译字段

这样新增一个模型后，不需要再专门开发一整套页面。

## 7. 对当前项目的恢复建议

### 7.1 不建议“直接回滚到旧 products/news 表方案”

原因不是旧思路错，而是当前项目已经发生了这些变化：

- 多语言翻译已经接入
- 模板系统已经绑定到当前栏目体系
- 静态生成已经大量依赖 `columns`
- 后台栏目树和内容页已经围绕 `columns` 重构

如果直接粗暴回滚，很容易出现：

- 栏目树恢复了，但模板上下文错乱
- 内容编辑恢复了，但多语言断掉
- 静态生成还在读统一表，导致数据不一致

更稳妥的方式应该是：

- 保留 `columns` 作为栏目表
- 把“内容记录”从 `columns` 中重新拆出去
- 让 `content_models` 真正接管内容层

### 7.2 建议分三阶段恢复

#### 第一阶段：先把架构关系拨正

目标：

- `columns` 只表示栏目
- 增加 `columns.content_model_id`
- 保留 `content_models` / `content_model_fields`
- 停止新增内容继续写入 `columns`

这一步先解决“职责混乱”。

#### 第二阶段：把产品/新闻恢复为模型表

目标：

- 建立新模型内容表
- 把 `product_item` / `news_item` 从 `columns` 迁出
- 后台列表和编辑改为按模型表读取

这一步先把现有两类内容恢复正常。

#### 第三阶段：开放用户自定义模型

目标：

- `/admin/content-models` 支持新增模型
- 支持新增字段
- 支持自动建表
- 栏目可绑定用户模型
- 内容编辑页动态生成

这一步才是真正接近你要的“帝国式内容模型”。

## 8. 推荐的最终数据分层

建议最终分成四层：

### 8.1 栏目层

- `columns`
- `column_translations`

职责：

- 树结构
- 导航
- 路由
- 栏目类型
- 模型绑定
- 模板绑定入口

### 8.2 模型定义层

- `content_models`
- `content_model_fields`

职责：

- 定义有哪些模型
- 每个模型有哪些字段
- 每个字段如何编辑、是否翻译、是否列表展示

### 8.3 内容数据层

- `content_<model>`
- `content_<model>_translations`

职责：

- 存真实内容数据

### 8.4 模板与生成层

继续保留现有：

- `templates`
- `template_variants`
- `template_bindings`

但模板上下文应改为：

- 栏目上下文来自 `columns`
- 内容上下文来自模型表

## 9. 这份分析对应的结论

简化成一句话就是：

- 你想要的方向是对的。
- 当前项目确实改偏了，已经从“栏目统一 + 模型独立”走成了“栏目和内容统一塞进 columns”。
- 最合理的修正方式不是简单回滚，而是恢复成：
  - `columns` 只管栏目
  - `content_models` 真正管理模型
  - 每个模型拥有自己的内容表
  - 栏目绑定模型
  - 后台按模型动态渲染内容管理

## 10. 建议的下一步

建议下一步不要直接动代码，而是先再出一份实施设计文档，至少明确这些问题：

1. `columns` 最终保留哪些字段，哪些字段必须迁出。
2. 内容模型表的最小 schema 是什么。
3. 多语言内容表如何设计。
4. 产品/新闻现有数据如何从 `columns` 迁回模型表。
5. 后台是先保留产品/新闻专用页过渡，还是直接切换到通用模型页。
6. 静态生成器读取内容的入口如何改。

如果按稳妥路线，我建议下一份文档直接写成：

- “栏目 + 内容模型重构实施方案”
- 按数据库、后端 API、后台页面、静态生成、迁移脚本五个部分拆开。
